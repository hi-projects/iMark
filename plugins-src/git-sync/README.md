# 定时上传（Git）

按固定间隔把当前仓库提交并推送到一个或多个 Git 远端（GitLab / Gitee / GitHub / 自建均可）。
需要本机安装 `git` 2.28 或更高版本（自动初始化仓库使用 `git init -b`）。

## 它做什么

每次同步依次执行：

1. 把编辑器里尚未落盘的文档写回磁盘；
2. `git add -A` + `git commit`（有改动才提交）；
3. 把同一个提交推送到**所有**配置好的远端。

推送一律直接把仓库地址交给 `git push`，**不会改动你仓库的 remote 配置**，也不会把访问令牌
写进 `.gitignore`、`.git/config` 或任何提交里 —— 凭据由每次现挂的一次性 credential helper 提供。

## 远端怎么填

**远端列表按仓库分别保存**：在仓库 A 里填的远端只属于 A，切换到仓库 B 后填写的就是 B 自己的列表；
两边互不影响。其它设置（同步间隔、代理、提交身份等）仍然是全局一份。

| 栏目 | 说明 |
|---|---|
| 远程仓库 | HTTPS 或 SSH 地址。SSH 形如 `git@host:用户名/仓库.git` |
| 本地分支 | **必填**，要推送的那条本地分支（如 `main`） |
| 远程分支 | 留空表示与本地分支同名 |
| 认证方式 | 访问令牌 / 账号密码 / SSH（用本机密钥，无需填密钥） |

访问令牌在对应远端那一行单独填写，经系统加密后保存（Windows 用 DPAPI）。
令牌与密码分开存放，来回切换认证方式不会互相覆盖。

## 网络代理

git 用的 libcurl **不会读取 Windows 的「系统代理」**，所以会出现一个很迷惑的状态：
浏览器能打开 GitHub，这个扩展的「测试连接」却一直超时。

扩展设置里的「网络代理」只决定**怎么找代理**，找到就用，找不到就直连：

| 连接方式 | 行为 |
|---|---|
| 自动检测本机代理（默认） | 先看 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` 环境变量，再读 Windows 系统代理（Clash、FlClash 等客户端开启「系统代理」时写入的同一个设置） |
| 手动指定代理 | 使用下面填写的地址，支持 `http://`、`https://`、`socks5://`；地址为空或无法识别时按直连处理 |

直连是两种方式的默认兜底，不需要单独开关。

代理会通过 `-c http.proxy=…` 只交给 git 的网络操作（推送、测试连接），**不改动你的全局 git 配置**。
回环地址（`127.0.0.1`、`localhost`）与 `NO_PROXY` 命中的地址不会走代理。

代理**只作用于 HTTP(S) 远端**。`git@host:…` 或 `ssh://` 地址由 ssh 自己建立连接，不经过 HTTP 代理；
要通过本机代理访问 GitHub，请把远端地址换成 HTTPS 形式。

不知道本机代理是什么、或想确认它是否在运行，可以点扩展设置里的「检测本机代理」。

## 首次使用

仓库还不是 git 仓库时，可在设置里打开「自动初始化仓库」：扩展会 `git init -b main`，
并可选地写入一份推荐的 `.gitignore` 与一个 `README.md`（**已有文件一概不覆盖**）。

初始化后请在「远端仓库」里填上地址与访问令牌，再点一次「立即上传」。

## 关于权限

这个扩展的 **main 层是 node 模式**，在 iMark 主进程里运行，需要 `git`、`secrets`、`vault:read`、`vault:write` 四项权限，
也就是说它具备与本应用相同的文件读写能力。它对密钥的使用方式是只读的，且只能读到自己的密钥，
但 node main 本身拥有完整 Node 权限、**不是沙箱** —— 请只安装你信任来源的扩展。
