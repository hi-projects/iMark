# 远程同步

按固定间隔在本地仓库与一个 Git 远端之间双向同步（GitHub / GitLab / Gitee / 自建均可）。
需要本机安装 `git` 2.28 或更高版本（自动初始化仓库使用 `git init -b`）。

## 它做什么

「立即同步」每次依次执行：

1. 把编辑器里尚未落盘的文档写回磁盘；
2. `git add -A` + `git commit`（有改动才提交）；
3. 从远端拉取配置的分支，快进或合并到当前分支；
4. 把合并后的本地分支推送回远端。

也可以只做一半：

| 命令 | 行为 |
|---|---|
| 立即同步 | 提交 + 拉取合并 + 推送；自动同步（间隔 > 0）走的也是这条路 |
| 上传文件 | 只提交并推送，不拉取 |
| 拉取文件 | 本地未提交改动先临时 stash → 拉取合并 → 恢复 stash；不提交、不推送 |

「拉取文件」恢复 stash 时如果和远端改动冲突，会保留冲突标记并打开冲突界面；
不会产生本地提交，也不会推送。

如果**远端合并本身**就冲突，本地未提交改动会先留在 stash 里；等你在冲突界面完成合并后点
「立即同步」，扩展会先补上合并提交，再自动恢复并提交 stash 里的本地改动。

拉取与推送都直接把仓库地址交给 git，**不会改动你仓库的 remote 配置**，也不会把访问令牌
写进 `.git/config`、命令行或任何提交里 —— 凭据由每次现挂的一次性 credential helper 提供。

## 下载与合并规则

- 本地已包含远端：什么也不做；
- 本地落后：快进（fast-forward）；
- 两边都有新提交：自动合并成一个合并提交；
- 自动合并产生冲突：**保留合并状态与冲突标记**，编辑器里会显示冲突界面（见下一节）；处理完再同步即可；
- 远端还没有配置的分支：不算错误，首次上传会创建它；
- 空仓库首次连接一个已有内容的远端：直接采纳远端分支（不会造一个空的本地根提交）；
- 配置的「本地分支」不是当前检出的分支时：同步/上传跳过下载但仍然推送；「拉取文件」会直接报错提示切换分支。
- 「拉取文件」遇到本地未提交改动时：先把改动存进临时 stash，拉取完成后自动恢复。
  恢复时与远端改动冲突 → 保留冲突标记并进入冲突界面。

扩展会在拉取/合并后让已打开的文件重新读取磁盘：下载的改动、冲突标记都会立刻出现在编辑器里，
不需要手动刷新。仍有未保存改动的文档不会被覆盖。

## 处理合并冲突

冲突时每个文件里会保留三行标记（`<<<<<<<` / `=======` / `>>>>>>>`），编辑器把它们渲染成
类似 VSCode 的冲突界面：

- 标记行换成一条操作栏，显示「冲突 i/n」「当前更改（分支名）」；
- 当前版本与传入版本分别用绿、蓝底色标出；
- 每处冲突都有三枚按钮：**接受当前** / **接受传入** / **保留两者**；
- 状态栏显示「N 处冲突」，点击跳到下一处。

选择后文档里的标记立即被替换，和普通编辑一样可以撤销。所有冲突处理完后，再点「立即同步」：
扩展会发现合并还没收尾，先检查文件里是否还有冲突标记，确认处理干净后完成合并提交，再继续推送。

如果冲突发生在**没有打开在编辑器里的文件**（典型是 `.gitignore`），扩展会自动弹出
「处理合并冲突」窗口：左侧是文件列表，右侧逐处展示当前/传入两段内容与三枚按钮；
处理完点「保存并继续同步」，会先写回磁盘，再自动继续完成合并并推送。
编辑器里已经打开的文件使用上面的内联操作栏，不会重复弹窗。
关掉窗口后，也可以在命令面板里执行「处理合并冲突」随时重新打开。

只要还有冲突标记，扩展**不会**把工作区提交上去；也不会用 `-X ours` / `-X theirs`
替你丢掉任何一边的改动。

## 远端怎么填

**远端配置按仓库分别保存**：在仓库 A 里填的远端只属于 A，切换到仓库 B 后填写的就是 B 自己的远端；
两边互不影响。其它设置（同步间隔、代理、提交身份等）仍然是全局一份。

从旧版本升级时，历史配置里的多个远端只会使用**第一个填了地址的行**；设置页也只显示这一行，
编辑任意字段后配置会收敛成一行。

| 栏目 | 说明 |
|---|---|
| 远程仓库 | HTTPS 或 SSH 地址。SSH 形如 `git@host:用户名/仓库.git` |
| 本地分支 | **必填**，要同步的那条本地分支（如 `main`） |
| 远程分支 | 留空表示与本地分支同名 |
| 认证方式 | 访问令牌 / 账号密码 / SSH（用本机密钥，无需填密钥） |

访问令牌填在远端表单里，经系统加密后保存（Windows 用 DPAPI）。
令牌与密码分开存放，来回切换认证方式不会互相覆盖。

## 网络代理

git 用的 libcurl **不会读取操作系统的「系统代理」**，所以会出现一个很迷惑的状态：
浏览器能打开 GitHub，这个扩展的「测试连接」却一直超时。

扩展设置里的「网络代理」只决定**怎么找代理**，找到就用，找不到就直连：

| 连接方式 | 行为 |
|---|---|
| 自动检测本机代理（默认） | 先看 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` 环境变量，再读系统代理：Windows 读注册表的 Internet Settings，Linux 读 GNOME 的 gsettings（Clash、FlClash 等客户端开启「系统代理」时写的就是这两处） |
| 手动指定代理 | 使用下面填写的地址，支持 `http://`、`https://`、`socks5://`；地址为空或无法识别时按直连处理 |

直连是两种方式的默认兜底，不需要单独开关。

代理会通过 `-c http.proxy=…` 只交给 git 的网络操作（下载、推送、测试连接），**不改动你的全局 git 配置**。
回环地址（`127.0.0.1`、`localhost`）与 `NO_PROXY` 命中的地址不会走代理。

代理**只作用于 HTTP(S) 远端**。`git@host:…` 或 `ssh://` 地址由 ssh 自己建立连接，不经过 HTTP 代理；
要通过本机代理访问 GitHub，请把远端地址换成 HTTPS 形式。

不知道本机代理是什么、或想确认它是否在运行，可以点扩展设置里的「检测代理」。

## 首次使用

仓库还不是 git 仓库时，可在设置里打开「自动初始化仓库」：扩展会 `git init -b main`，
并可选地写入一份推荐的 `.gitignore` 与一个 `README.md`（**已有文件一概不覆盖**）。
空仓库第一次连接已有内容的远端时，会先采纳远端再写这些脚手架，因此不会与远端自带的
`.gitignore` / `README.md` 冲突。

初始化后请在「远端仓库」里填上地址与访问令牌，再点一次「立即同步」。
空仓库连接已有内容的远端时，第一次同步会先把远端内容下载到本地。

## 关于权限

扩展代码跑在独立的 `utilityProcess` 扩展宿主里，以当前用户权限运行，**没有权限沙箱**。
清单里的 `filesystem: user`、`network`、`secrets`、`git`、`process` 是安装时的披露，
不是运行时门禁。它只读取自己的密钥，但宿主本身拥有完整的 Node 能力 —— 请只安装你信任来源的扩展。
